# DESIGN_DECISIONS.md

**WHAT THIS FILE DOES:** Records every place this build had to invent something Klarna hasn't disclosed, what the alternative was, and why the final choice won — including cases where an earlier draft of this design disagreed with the final call.

---

**DD-001 — Intent classification location.** Classification lives inside Intake as one of two internal functions (`classify_intent`, `extract_claim_details`), not as a separate top-level step. Klarna's own materials don't distinguish a classification step from "handling" a query, so there's no confirmed basis to split it out further. Low controversy.

**DD-002 — Escalation reason ownership.** Reasons are split into two categories with different owners: structural failures (`unclassified`, `no_record`, `incomplete_claim`) are reported directly by the Orchestrator and never reach Gate; decision-level reasons (`mismatch`, `ambiguous_delay`, `low_confidence`) are Gate's alone. An earlier draft of this design listed `no_record` as one of Gate's possible outputs while simultaneously describing it as something the Orchestrator intercepts before Gate is ever called — those can't both be true, since a status Gate never sees can't be a reason Gate produces. Resolved by giving each reason exactly one owner.

**DD-003 — Gate's decision criteria and reason set.** Gate auto-resolves only when the relevant field matches the record *and* Intake's confidence clears the threshold; anything else escalates. The reason set is `mismatch`, `ambiguous_delay`, `low_confidence` — a `high_value_flag` reason was considered and cut entirely. **Disagreement preserved:** an earlier draft argued for simplifying further, to match-plus-confidence only, dropping `ambiguous_delay` as well as `high_value_flag`, on the reasoning that fewer invented criteria are more honest than more. That simplification was rejected — the illustrative scenario this repo is built around (a payment that posted late due to a processing delay outside the customer's control) has no code path under the simpler version. `ambiguous_delay` stays because the scenario it's built around needs it to exist; `high_value_flag` is cut because nothing in either the confirmed function list or the scenario ever needed it in the first place — it was invented on top of an already-invented decision, with no textual anchor at all.

**DD-004 — Fail-fast vs. gate-evaluated.** A record that can't be found or checked at all (no record, incomplete claim) fails fast before Gate is invoked. A record that was found and checked — whether it matches or not — reaches Gate, because only Gate is positioned to decide whether a disagreement with the record is grounds for escalation or something else.

**DD-005 — Confidence threshold (0.6).** Arbitrary, `[DEV]`-marked in code with an explicit instruction: this value is not derived from any Klarna data or tuning process, and whoever adopts this repo should replace it with a value suited to their own data. Kept at 0.6 specifically for consistency with this series' prior precedent, not because 0.6 is defensible on its own.

**DD-006 — Dispute-type scope.** Illustrative scope is narrowed to `late_fee_dispute`, `refund_request`, `unclassified`. Two categories considered and rejected: a "payment reschedule" type, dropped because it's a forward-looking account action rather than anything in Klarna's confirmed dispute/refund/invoice-inaccuracy list; and a "cancellation" type, which is confirmed but left out of scope, since the illustrative scenario this repo demonstrates never exercises it. This is a stated scope decision, not an oversight — the repo demonstrates two of Klarna's confirmed functions end-to-end rather than all of them shallowly.

**DD-007 — Per-dispute-type claim field relevance.** `late_fee_dispute` requires and compares only `claimed_date`; `refund_request` requires and compares only `claimed_amount`. **Disagreement preserved:** the alternative was checking both fields uniformly regardless of dispute type, which was rejected because it would make `refund_request` functionally unusable — customers disputing a refund amount rarely state a date, so uniform field requirements would push nearly every real `refund_request` case into `incomplete_claim` regardless of whether the customer's message was actually complete for that kind of dispute.

**DD-008 — `mismatch_reason` naming and scope.** The generic mismatch label is `claim_mismatch`, not `date_mismatch` — a name that would be actively incorrect for a `refund_request` case, which never compares a date at all. `processing_delay_noted` (and therefore Gate's `ambiguous_delay` reason) is scoped to `late_fee_dispute` only — the record-level delay flag describes a payment posting late, which has no equivalent meaning for a refund-amount question.

**DD-009 — Amount-only mismatch handling.** An amount disagreement (relevant only to `refund_request` under DD-007) is reported as `claim_mismatch`, the same generic label used for a date disagreement — no separate `amount_mismatch` value exists. Kept this way because the scope stays deliberately narrow (DD-006); a future adopter extending this repo to test finer-grained mismatch types has a clear seam to split at, marked `[DEV]`.

**DD-010 — Keyword-collision tiebreak.** When a message's keywords match both dispute types, `late_fee_dispute` wins as the assigned type, and `confidence` drops to `0.5` regardless of which type won, signaling genuine ambiguity rather than a clean classification. `[DEV]`-marked — arbitrary and deterministic, not defended as the "correct" priority.

**DD-011 — Confidence computation.** Confidence is a small set of discrete values (`0.9` / `0.5` / `0.0`) tied to match quality, not a continuous score. A rule-based, keyword-matching classifier can report actual ambiguity (multiple keyword sets matched) but has no basis for reporting graduated uncertainty the way a probabilistic model would — a continuous score here would imply more precision than keyword matching can honestly produce.

**DD-012 — Gate reason precedence (mismatch before confidence).** When a case is both a record mismatch and low-confidence, Gate reports the mismatch-family reason, never `low_confidence`. Rationale: a disagreement with Klarna's own record is a finding about the claim itself; low confidence is a finding about Intake's own uncertainty. The two aren't the same kind of problem, and a human agent seeing `low_confidence` should be able to trust it means "we weren't sure what was being asked," not "we checked and it's also wrong" — collapsing the two into one signal would make `low_confidence` a strictly less useful flag for the person doing the reviewing.

**DD-013 — Verification-level precedence (record lookup before completeness check).** When a customer can't be found *and* the claim is incomplete, Verification reports `no_record`, not `incomplete_claim`. **Disagreement preserved:** the first draft of this logic checked completeness before looking up the record, purely because it's the cheaper check computationally. That ordering was reconsidered and reversed — an unrecognized customer is a categorically more serious finding than a vaguely-worded message (potential account mismatch or wrong ID, versus a customer who simply didn't specify enough detail), and that priority is worth one avoidable lookup call on cases that turn out incomplete anyway.

**DD-014 — Comparison semantics and the missing `customer_id` parameter, found during implementation.** Two things surfaced only once code had to actually run, after four design review passes had already signed off:

1. `run_verification`'s signature was specified everywhere as `run_verification(intake_result)`, with no way to receive a `customer_id` — even though `lookup_record` needs one and `IntakeResult` has nowhere to carry it (customer identity is supplied by the caller, not extracted from the message). Fixed to `run_verification(intake_result, customer_id)`.
2. What exactly gets compared to what was never made explicit at the field level. Resolved as: `late_fee_dispute` compares `claimed_date` to the record's `payment_date`; `refund_request` compares `claimed_amount` to the record's `amount_paid`. These are the most direct readings available, not independently re-litigated design choices — flagged here because they were made at the keyboard, not at a review table, and that distinction is worth being honest about.

Both are recorded here as a reminder that a specification passing review is not the same claim as a specification being complete — the actual build-and-test discipline this series follows exists specifically because this gap class survives prose review and doesn't survive code.

## Scope Statement

This build demonstrates two of Klarna's six confirmed customer-service functions (Section 3.1 of the accompanying case study) end-to-end, with full test coverage of every decision path each one touches. It does not attempt shallow coverage of all six. Every mechanism beyond the confirmed function list is an explicit, labeled invention — never presented as a disclosure of Klarna's actual system.
